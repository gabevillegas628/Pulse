Pulse · reference

The codebase map

What started as an iClicker replacement is now a live-questions tool, a homework system, a gradebook, a textbook reader, and a PowerPoint add-in sharing one server and one database. This page is the floor plan: every room, what it's for, and which hallways connect them.

The shape of it

Pulse is a monorepo with one deployable unit. In production a single Node process serves everything: the REST API, the socket.io hub, the built React frontend, and the built PowerPoint task pane — all one origin, which is what lets the add-in pages share auth with the app. Railway runs it; Postgres sits behind it via Prisma; a separate Indigo container handles chemistry.

The domain has exactly two lanes that share their atoms. A Session is an in-class deck — answers are live, final, and socket-broadcast. An Assignment is homework — answers are drafts until submitted, with deadlines and per-student extensions. Both lanes are built from the same Question and Response tables, and nearly every student-facing route branches once on which lane a question belongs to. Hold that split in your head and most of the backend reads itself.

The vocabulary

The mental map is mostly the data model. Sixteen models, but really five ideas: people (Professor, Student), the container (Class, Section, Enrollment), the two lanes (Session + SessionRun vs Assignment + DeadlineExtension), the shared atoms (QuestionGroup, Question, Response), and the AI layer (ThemeSet, ThemeCategory, ResponseTheme).

The subtlest distinction — and the one worth re-learning — is Session versus SessionRun. A Session is a template: the deck of questions, reusable across terms and sections. A SessionRun is one occurrence of it, opened for a section (or the whole class), and it is what actually opens and closes. Responses stamp the run they landed in, which is how the same session taught twice keeps its answer sets apart.

A lecture, end to end

  1. The professor opens a run

    POST /sessions/:id/runs, scoped to a section or the whole class. run_status goes out to the session room; the deck's printed QR codes are already live because codes belong to questions, not runs.

  2. Students scan in

    The QR resolves to /q/code/:code. The server accepts it only if a run is open for that student's section — the lookup joins their enrollment, so section B can't answer section A's run.

  3. An answer lands

    POST /responses: final, stamped with the run, one per student per question. First contact with a class auto-enrolls the student — nobody fails to answer over paperwork.

  4. The server fans out

    Three side-effects per answer, none of which can fail the student's request: the professor room gets new_response (with identity and clock state), the close clock is touched if armed, and theme work is debounced onto the queue if enabled.

  5. The room watches the slide

    /present, framed inside PowerPoint, asks /addin/live "what's open right now?" and follows the class automatically. Below the answer threshold it shows presence dots; with themes on, bars grow as Haiku classifies; with a clock armed, the countdown bar drains and resets.

  6. Things close

    A timed question closes itself when the room goes quiet (question_closed; the professor can reopen). The run closes when the professor closes it — or when the scheduler's 100-minute sweep does. Closing the run drops its clocks and freezes its theme set.

  7. Afterwards

    The professor runs AI grading per question (progress streams over the socket), overrides scores where the model was wrong, and the gradebook and student grade views pick it all up.

Homework is the same skeleton with the tempo changed: answers upsert as drafts, an explicit submit locks them, the deadline (extension-aware) is enforced server-side on every write, and grades appear once the assignment closes.

How grades are computed

One function owns it: gradeSession() in backend/src/utils/scoring.ts. Every question scores 0–1. An aiScore on the response — whether the model's or a professor override — always wins. Without one, objective types self-grade: numeric answers compare with tolerance and unit conversion via mathjs, structures compare as InChI strings, choice types compare literally. Free text only ever gets a score from AI participation grading (full / partial / no credit).

A question counts toward earned/max only if the professor set it up for grading (a key exists, or AI grading was run) — and, for in-class questions, only if it was actually presented to that student's section, which is inferred from responses existing in the section's runs. That last rule is what keeps a two-section course from penalising section B for a question only section A saw.

The projector invariant

Anything that can appear on a lecture-hall wall — /present, ResultsSummary, ThemeBars, the /addin/live payload, the session-room socket events — carries aggregates only: counts and shares, never a student's name, netId, or raw answer. Identity flows exclusively through the :professor room and professor-guarded REST. When adding anything to the projector path, this is the invariant to keep.

The frontend, route by route

Routing lives in App.tsx; state is react-query over the axios client in api/client.ts. Two parallel auth contexts (professor, student) can be logged in simultaneously; the client injects whichever token fits, with a third fallback token for pages rendered inside PowerPoint, whose storage partition can't see the browser's. A 401 anywhere raises the session-expired modal instead of silently dumping work.

The PowerPoint add-in

Two pieces with opposite philosophies, both in addin/. The task pane is the pre-lecture tool: it inserts question QR cards as ordinary tagged pictures (static PNGs — they work offline, print, and can't fail to load mid-lecture), checks a whole deck's codes against /api/addin/verify, and re-binds them at semester rollover. The Live Results object is a content add-in that frames /present on a slide: live by nature, so instead of a static fallback it degrades to a readable status line. Slides bind to questions by accessCode, and the tags live inside the .pptx itself — keeping decks true across saves, copies, and terms is the add-in's whole job.

Sharp edges

One process, or nothing works

Close clocks, theme debounce timers, and socket rooms all live in RAM. A second instance would silently break all three. warmFromDb() covers restarts; nothing covers replicas.

responses.routes.ts is misnamed

It's the whole student API. The run-resolution, deadline-with-extension, and enrollment checks are each repeated three to four times inside it — extract before extending.

The XOR parent

Every student route branches on session-vs-assignment. Tolerable at this scale, but each new student endpoint pays the two-lane tax. Write both branches or reject one explicitly.

Answer key leaks to students

GET /student/assignments/:id returns correctAnswer while homework is open, and a leftover Debug panel in AssignmentPage.tsx renders it. Strip both.

Dead and vestigial code

SubmitPage.tsx (367 lines) is routed nowhere. Session.accessCode is unused. The add-in spike (spike.html, spike manifest) is on the backlog to delete, as is root clutter like migrate_structures_q.sql.

Grade math exists twice

Backend utils/scoring.ts and frontend lib/scoring.ts implement the same rules. A change to one without the other shows students different numbers than the gradebook.
