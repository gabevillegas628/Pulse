The close countdown

A question that shuts itself once the room stops answering — and restarts its clock every time someone does. Here is exactly when it closes, and the five numbers that decide.

The rule in one line

A timed question closes when it has been quiet for about three typical gaps — where "typical" is measured from how fast that particular question is actually drawing answers — but never sooner than 20 seconds after its first answer.

Everything else below is that sentence's consequences.

The flow

  1. Nothing runs until the first answer

    A timed question with no answers has no clock and no deadline. It cannot close, the projector shows no bar, and the first answer is never refused. Opening a question does not start anything — the room does.

  2. The first answer starts a 20-second window

    One arrival says nothing about pace, so the grace falls back to its minimum and the floor is what actually holds the question open. The bar appears, full, at 20 seconds.

  3. Every answer after that re-measures the room

    The gap since the previous answer joins a rolling history of the last 64. The grace becomes the median of those gaps times three, clamped to between 8 and 45 seconds. A question drawing answers every second gets a short leash; one drawing them every fifteen gets a long one.

  4. The deadline moves out, or holds — never in

    The close is the latest of three things: where it already was, the last answer plus the grace, and the first answer plus the floor. Because the first of those is in the list, an answer can only ever buy time. It can never cost any.

  5. At zero, the server stops accepting

    The check runs at submission, so a stale browser tab, a replayed request and a written-down access code all hit the same wall. Only now does the projector reveal which answer was correct — while the question is open, the answer key is not in the payload at all.

  6. You can always give them more time

    The button in the session sidebar restarts the clock from now, whether or not it has already run out. It is the reason an automatic close is safe to make binding: the rule holds unless you deliberately lift it.

Why the bar sits still, then starts jumping

This is the one behaviour worth understanding before you teach with it. Early answers do not extend the deadline — not because they are ignored, but because the floor already reaches further than the grace does. The reset only bites once the grace overtakes it.

What this means for the room

The reset is only visible while the grace is binding. Every second of floor is a second where answering demonstrably does nothing — so the floor should be as short as your room tolerates, not as long as feels safe. If the opening stretch feels dead on the wall, FLOOR_MS is the number to cut.

What you can tune

Behaviour — backend/src/services/clock.service.ts

ConstantNowWhat moving it does
FLOOR_MS 20s Minimum a question stays open, measured from its first answer. The single biggest lever on how the wall feels. Lower it and the reset starts mattering sooner; raise it and the room gets more reading time but a longer dead stretch.
GRACE_GAPS 3 How many typical gaps of silence end the question. Two closes briskly and risks cutting a lull; four is forgiving and slower.
MIN_GRACE_MS 8s Shortest possible grace — and also the fallback before any pace is known, which is why it sets that opening window with the floor.
MAX_GRACE_MS 45s Longest possible grace, so a slow trickle cannot hold the room indefinitely.
MAX_GAPS 64 How many recent gaps the median is taken over. Lower makes the clock react faster to the pace changing; rarely worth touching.

If you change a constant

smoke-autoclose.ts asserts against these values deliberately, so a change fails the suite loudly rather than drifting unnoticed. Update the mirrored constants at the top of that file in the same edit, then run npm run test:smoke:autoclose.

What holds no matter what

An answer never costs time

The deadline is clamped monotonic. It moves out or holds; it cannot move in. Without this the second answer of a question pulled the close 25 seconds earlier.

The first answer is never refused

No clock exists until one lands, and a question with no clock is open.

A restart does not un-time anything

Clocks rebuild at boot from the answers already recorded. A server down past a deadline finds that question correctly closed.

New run, new clocks

Closing the run drops every clock in it. Nothing carries into next term.

Untimed questions are untouched

With the toggle off, behaviour is exactly what it was — including the answer key showing live on the wall.

The answer key waits for the close

While a timed question is open, correctAnswer is absent from the projector payload entirely — not merely hidden in the UI.

Two limits worth remembering: the clocks live in one server process, so this breaks if Pulse is ever run on more than one instance; and nothing is recorded afterwards, so you cannot later prove a question was closed.
